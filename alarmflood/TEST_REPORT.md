## 2. 被测系统与测试范围

### 2.1 系统构成

三层五模块的单向数据流：

```
metric / 告警源
   │  loaders/loader_aiops2021.py     数据源 → 统一五列告警流
   ▼
[1] M1 modules/m1_templater.py        模板归并（drain3）
   ▼
[2] M2 modules/m2_window.py           洪水窗口检测 + 三级分诊（core/semi/novel）
   ▼
[3] M3 三条路线                       路线A m3_rank(规则) / 路线B m3_llm(LLM) / 路线C m3_fusion(融合)
   ▼
[4] M4 modules/m4_report.py           处置单 + 工单 + 幻觉校验
   ▼
[5] M5 app.py                         Streamlit 看板（两页签，只读产物）
```

**文件即接口**：模块之间以 parquet / JSON 约定交接，下游不直接 import 上游的计算函数（`app.py` 仅复用 `m3_rank.rank_entities` 做展示）。

## 4. 测试数据与评测协议

### 4.1 数据规模（实测）

| 指标 | 值 |
|---|---|
| 告警流（去重抑制后） | **14,806 条** |
| 涉及实体 | 14 |
| 告警种类（规则命中数） | 7 |
| 归并后模板数 | **7** |
| **模板压缩比** | **99.95%** |
| 三级分诊 | core **13,021** / semi **1,645** / novel **140** |
| 洪水窗口 | **895**（窗口规模：最小 1 条 / 中位 2 条 / 最大 9 条） |
| M4 处置单 | **111** 份（占窗口 12.4%，覆盖告警量最大的窗口） |

> **关键事实**：novel（新发）告警仅占 **0.95%**（140/14,806），其 99% 是常驻/半常驻背景噪声。
> 这正是"三层分诊"设计的依据。

### 4.2 评测协议（如实披露）

只评「**可检测故障**」，三层漏斗：

| 层 | 数量 | 说明 |
|---|---|---|
| groundtruth 全部故障 | **159** | train 112 / test 47 |
| train 中有重叠洪水窗口 | **89** | 排除 23 个（无对应告警窗口，如网络故障无告警） |
| **其中根因实体在窗口证据内** | **72** | ← **对比表分母** |

**为什么不评全部 159 个**：如果窗口内根本没有根因实体的任何告警证据，任何排序方法都无法定位，
把它计入分母只会掩盖真实方法差异。这是文献常用做法，本报告如实披露。

## 6. 算法指标（对应"核心功能完整、效果可验证"）

### 6.1 主对比实验表

四行同口径（均按「对**窗内全部实体**排名」计算），分母统一为 72：

| 方法 | Top-1 | Top-3 | 评测窗口数 | 说明 |
|---|---|---|---|---|
| **freq**（最笨基线） | 19/72 (26%) | 38/72 (53%) | 72 | 只按告警条数排序 |
| **rule**（路线A） | 34/72 (47%) | 45/72 (62%) | 72 | 0.50×新发数 + 0.15×新发最早 + 0.20×分层加权频次 + 0.15×活跃度 |
| **llm**（路线B，glm-4-plus） | **35/72 (49%)** | **47/72 (65%)** | 72 | tier 层级作显式线索 + 窗口概况摘要 + 输出根因实体 |
| **fusion**（路线C） | 33/72 (46%) | 45/72 (62%) | 72 | α·rule + (1−α)·LLM，α 按 5 折交叉验证选取 |

**结论**：

1. **LLM 路线最优**（49% / 65%），相对最笨基线提升 **+22pt Top-1 / +12pt Top-3**
2. LLM 相对 rule 提升 **+1pt Top-1 / +3pt Top-3**（Top-1：35 vs 34 个窗口；Top-3：47 vs 45 个窗口）—— 差距不大，说明**规则路线作为可审计保底是有效的**
3. **融合未超越最强单路线**（46% < 49%）——这是**诚实的负结果**，见 6.4

### 6.2 分类型明细（rule 路线）

| 故障类型 | Top-1 | Top-3 | 窗口数 | 解读 |
|---|---|---|---|---|
| **CPU** | 23/24 (**96%**) | 24/24 (100%) | 24 | 根因有专属新发告警，证据干净 |
| JVM | 6/10 (60%) | 7/10 (70%) | 10 | 中等 |
| MEMORY | 3/7 (43%) | 5/7 (71%) | 7 | 无专属证据，靠弱证据推理 |
| DISK | 2/11 (18%) | 6/11 (55%) | 11 | 磁盘新发告警稀疏 |
| **NETWORK** | **0/20 (0%)** | 3/20 (15%) | 20 | ⚠️ 天花板（原因见 8.2） |

LLM 路线分类型：CPU 96%/100% · JVM 60%/70% · MEMORY **57%/71%** · DISK 18%/55% · NETWORK 0%/20%。
**LLM 的主要增量在 MEMORY**（57% vs rule 43%）。

### 6.3 消融实验

| 消融项 | Top-1 | Top-3 | 结论 |
|---|---|---|---|
| llm 完整上下文 | 35/72 (49%) | 47/72 (65%) | 基准 |
| **llm 截断喂**（只喂最早 5 条证据） | 28/72 (39%) | — | **性能明显下降**，证明"上下文不可省"：判别性新发告警通常出现在常驻背景告警之后，砍掉后段等于砍掉证据 |

### 6.4 融合方法的负结果（如实记录）

| 项 | 值 |
|---|---|
| 全量调优最优 α | 0.0（即退化为纯 LLM） |
| 全量调优成绩（**有偏，不作结论**） | 35/72 (49%) / 47/72 (65%) |
| **5 折交叉验证（无偏）** | **33/72 (46%) / 45/72 (62%)** |
| 各折选中的 α | [0.0, 0.5, 1.0, 0.0, 0.0] |

**结论**：在当前数据上，两条路线的分歧多为"一错一对"（融合救回 0 个单路都漏的窗口、弄坏 1 个），
简单加权无法自动择善；且 72 个窗口的评测集偏小，α 选择噪声大（5 折选了 3 个不同 α）。
**这是记录在案的负结果**，未做美化。详见 `results/fusion_experiments.md`。

### 6.5 L2 真实监控栈试点实测（自建 Prometheus，非公开数据集）

> 数据来源：云服务器上自建的 Docker 监控栈（Prometheus + Alertmanager + `svc-api-1/2/3 → svc-db`），
> **故障由人工注入、真值已知**。这是"接入一个新告警源需要改多少代码"的实证。
> 复现：`python loaders/loader_prometheus.py` 然后 `python scripts/run_pilot_eval.py`

| 指标 | 实测值 |
|---|---|
| 告警通知条数 | **27** |
| 涉及实体 / 触发规则 | 4 / 2 |
| 归并后模板数 | **2** |
| **模板压缩比** | **92.6%**（2 个模板覆盖 27 条通知） |
| 重复报警占比 | 85.2% |
| 检测到的事件窗口 | 1 个（4 分钟） |
| **根因 Top-1** | **1/1 命中**（`svc-db`，score 1.000；第二名 `svc-api-2` 仅 0.175） |

**这条证据的价值**：把一个新的告警源（Prometheus / Alertmanager）接进系统，
**只新增了一个 `loaders/loader_prometheus.py`，M1→M4 全部模块零改动**——
"文件即接口"的约定在真实数据上成立。

**必须如实说明的局限**：

1. **样本极小**：27 条告警、**只有 1 次故障注入**。Top-1 100% 的分母是 **1**，
   **不构成统计意义上的结论**，只能证明"链路在真实数据上跑得通，且能命中注入的根因"。
2. 告警条数 **27 < 30**（D6 计划的目标值），未达目标。原因是注入时长 180s ×
   `repeat_interval=30s` 只够产生这么多重复通知。
3. 重复报警占比 85.2% 与 AIOps2021 上的 84.8% 接近，说明 Alertmanager 的周期重发
   与真实运维中的"告警洪水"形态一致——这也是三级分诊设计在真实场景同样成立的理由。

## 8. 已知局限（答辩如实说明）

### 8.1 评测集规模小

可评测窗口仅 **72** 个。交叉验证每折验证集约 14 个窗口，指标波动较大；
融合方法因多一个超参数（α），在小样本下反而更不稳定（见 6.4）。

### 8.2 NETWORK 型天花板（已定位原因，本轮未修）

NETWORK 型占 train 故障的 **42%（47/112）**，是最大类别，但 Top-1 为 **0/20**。

**已查清原因**：告警规则中 3 条阈值从未生效 —— `SWP` 恒为 0（系统未启用 swap）、
`NETBandwidthUtil` 是 0~1 比例（10 天 max 仅 0.368）、`FSInodeUsedPercent` 逐日 max 恒为 29.9。

**已量化修正收益**：把失效的带宽指标换成 `NETWORK_TCP-FIN-WAIT` 后，网络型 Top-1 可从
0/20 提升到 16/46（35%）。但该修正会改变告警流、使已完成的 D3/D4 结果失效，
**为保持实验口径一致，本轮未启用**，完整记录见 `results/rule_audit.md`。

### 8.3 LLM 置信度未校准

融合时把 LLM 自报的 `confidence`（0.1~0.9 共 10 个离散值）直接与 rule 分数相加，
未做校准（isotonic / 分箱），这是融合未带来增益的原因之一。

### 8.4 数据与环境边界

- 主数据集许可为 **CC BY-NC 4.0（非商业性使用）**，商业转化需替换为自有数据
- 界面在 Windows 上实测；纯 Python 逻辑跨平台，但中文字体依赖 `SimHei`
- LLM 结果仅来自单一模型（glm-4-plus）、单次运行，未做多次采样平均
