## D2 观察与分析（2026-10-14）

### 1. 数据的关键事实：三级告警结构

M2 实测发现告警流呈三级分布（这是今天最重要的发现，直接推翻了指南原设计）：

| 层级 | 判据（总触发次数） | 数量 | 占比 | 例子 |
|---|---|---|---|---|
| core 常驻 | >=900 | 13,021 条（11 对） | 87.9% | 全体实体内存告警（Mysql01 1384 次/14 天） |
| semi 半常驻 | 100~899 | 1,645 条（5 对） | 11.1% | apache01 内存（5 天 485 次）、Mysql02 sdc 磁盘（15+ 天 118 次） |
| novel 新发 | <100 | 140 条（38 对） | 0.9% | CPU/磁盘/JVM 告警 |

**99% 的告警是背景噪声，真事件信号只占 0.9%**——指南的"mean+3σ 速率检测"被周期性常驻重触发淹没（检出 210 个 1 分钟碎窗）。改为三级分诊后：core 搁置、semi+novel 触发窗口、排序时三级权重（2.0/1.0/0.5）。

### 2. 结果解读

- **rule 比 freq 全面提升**（Top-1 +21pt，Top-3 +9pt）：新发告警为主证据的分层设计有效。频次基线被噪声大户（apache01/Mysql01 每 10 分钟一次常驻重触发）带偏。
- **分类型天花板差异巨大**（rule 路线）：
  - CPU: Top-1 23/24 (96%), Top-3 100% —— 根因有专属新发告警（如 Redis02 CPU 故障窗内唯一 novel 告警就是 Redis02 自己的 2 条），证据干净
  - JVM: 60%/70%；MEMORY: ~40%/70%（无专属证据，靠弱证据猜）
  - NETWORK: Top-1 0/20 —— **告警规则对网络故障完全失明**（D1 已知边界：OS 层网络指标无指纹），这 20 个"可评测"样本的根因只有常驻内存告警在窗内，排序等于随机
  - DISK: Top-1 2/11 —— 磁盘新发告警太稀疏（sda/sdb/sdc 全部 118 条里大头是 Mysql02 常驻）
- **失误案例的共同模式**：Top-3 里反复出现 apache01/Mysql01——它们是常驻告警最密集的实体，弱证据权重仍偏高。D6 调优方向：core 权重降到 0.2 或直接不参与排序（仅展示）。

### 3. 结论与后续

1. rule 路线 47%/62% 是**当前 10 条告警规则下的诚实上限附近**——CPU/JVM 型故障证据充分，NETWORK/DISK 型需要更底层的信号（trace 调用链、更多磁盘规则），属 D6 改进项
2. D3 的 LLM 路线有明确超越空间：LLM 能利用"Redis02 在窗口内独有 2 条新发告警且最早出现"这种上下文推理，也能对"全实体都只有常驻告警"的窗口输出低置信度——这是数值公式做不到的
3. 若 D3 LLM 显著优于 rule → 答辩叙事"LLM 推理 > 启发式公式"；若不显著 → 叙事"规则排序保底可审计，LLM 负责解释与处置"（预案不变）

## D3 观察与分析（2026-10-15）

> 注意：本文件 freq/rule 两行由 `modules/m3_rank.py` 生成，重跑会覆盖整表；上面 llm 两行与本节由 B 手工并入，A 重跑后需重新合并（或后续把 LLM 行纳入统一生成脚本）。

### 1. LLM 路线（glm-4-plus，智谱 BigModel）

分类型（llm）：CPU 96%/100% · JVM 60%/70% · MEMORY 57%/71% · DISK 18%/55% · NETWORK 0%/20%

### 2. 关键发现

- **prompt 决定成败**：首版 prompt（只给 tier 标签）Top-1 仅 25%，比 rule 还差；加上「窗口概况（列出哪些实体有新发告警）」摘要 + 「常驻=全天候背景噪声、几乎不是根因」的运维先验后，Top-1 升到 49%、Top-3 64%，反超 rule（47%/62%）。
- **LLM 与 rule 互补**：CPU/JVM/DISK 两路线基本持平；LLM 在 MEMORY 上明显更好（57% vs rule ~40%）——对"无专属新发告警"的窗口，LLM 的弱证据权衡比 rule 的固定权重更合理。
- **截断喂消融（25%）证明上下文不可省**：只喂最早 5 条证据时性能腰斩。原因是判别性的新发告警通常比常驻背景告警出现得晚，砍掉后段等于砍掉证据。
- **NETWORK 仍是天花板**：LLM 同样 0%（Top-3 20%），与 rule 一致——根因实体在窗口内只有常驻告警，任何排序方法都无从下手，须靠 trace 级信号（D6）突破。

### 3. 结论与后续

1. D3 目标达成：LLM 路线 49%/64% 作为最终方法候选，略优于 rule；MEMORY 类型的提升是主要增量。
2. 两套叙事均成立：数据支持"LLM 略优"，同时保留"rule 保底可审计 + LLM 负责解释/处置单"的兜底叙事（开工方案风险预案）。
3. 复现：`python modules/m3_llm.py --mode all`（密钥走仓库根 `.env`；对比结果落 `results/llm_experiments.md`，推理链落 `results/llm_examples.md`）。
