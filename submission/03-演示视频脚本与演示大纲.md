# 演示视频脚本 + 演示大纲（3~5 分钟版）

> 用途：D7 官方材料「3~5 分钟演示视频」的口播稿与操作大纲；也可作线下答辩 5 分钟版的骨架。
> 所有数字均已与 `results/experiments.md` 核对，**口径标注在括号内，口播时不必念出来，但被追问时要能答上**。
> 语速按每分钟 220 字设计，全文口播约 4 分钟，留 30~60 秒给画面呼吸与操作停顿。

---

## 一、口播稿（带时间轴）

### 0:00–0:30 开场：一个问题

> 这是某企业一次故障发生后的第一分钟。**三百多条告警同时涌进值班台**——同一台机器的内存告警反复刷屏，上下游服务的超时告警层层传导。值班工程师要做的第一件事不是修故障，而是在告警洪水里**捞出真正有用的那几条**。行业调研里，这个"从告警到定位根因"的过程平均要 40 分钟以上。
>
> 我们的作品，**AlarmFlood Copilot——告警洪水治理值班台**，把这条人工链路压缩到一次点击。

**画面**：跳切告警洪水滚动的录屏（可用全量时间轴页放大动画），最后定格标题页。

### 0:30–1:10 发生了什么：先治理洪水本身

> 系统的第一步不是找根因，而是**先把洪水降下去**。数据来自公开的 CCF AIOps 2021 故障数据集：十万零一千条原始指标告警，经过模板归并与重复抑制降到一万四千八百条，**压掉 85.4%**。
>
> 但更关键的发现是结构性的：这一万四千条里，**87.9% 是"常驻告警"**——长期反复触发的已知噪声；真正由故障带来的"新发告警"只占 0.9%。我们据此做了**三级分诊**：常驻的搁置、半常驻的降权、新发的主证据。刚才那三百条洪水，在这个窗口里被分诊成了：三到四条新发信号、少量半常驻，其余全是可安全忽略的背景噪声。

**画面**：时间轴页 → 选中一个窗口 → 三级分诊卡片（novel/semi/core 数字对比）。

### 1:10–2:00 谁是根因：双路互证

> 第二个问题，谁是根因。我们把同一批证据交给**两条独立路线**：
>
> 路线 A 是**确定性规则**：新发告警数为主证据、首现越早越可疑、分层加权频次——全程可复现、可审计，不依赖任何模型。
>
> 路线 B 是**大模型推理**：把窗口证据结构化后交给大模型，让它像值班专家一样推理"因果链上游是谁"。
>
> 在 72 个可评测故障窗口上（口径：存在可检测洪水窗口且根因实体在证据中），规则路线 Top-1 命中 **47%**，大模型路线 **49%**；而我们做的消融显示，把告警流直接截断喂给模型的朴素做法只有 39%——**结构化的证据组织比"直接喂给大模型"高了十个百分点**。
>
> 两条路线结论一致时，系统提示"可高置信派单"；分歧时自动触发人工复核。**AI 只建议，不拍板。**

**画面**：页签一，路线 A/路线 B 两列并排；选一个双路一致的窗口（如 #377/#41），展示 Top-1 卡片与一致性提示。

### 2:00–2:40 怎么办：处置单与人在回路派单

> 第三个问题，怎么办。根因确认后，系统生成**结构化处置单**：故障摘要、根因实体与置信度、分优先级的处置动作，全部要求**实体必须在窗口证据内**——大模型输出窗内不存在的实体会被判为幻觉、拒绝采用，这就是我们的幻觉校验。
>
> 派单是两步走：先生成工单预览——责任团队由根因实体查映射表自动得出；值班人**核对确认后才发送**。替代的是过去"查归属、写工单、发值班群"三步手工操作。批量场景下还能把全部窗口一键导出成工单清单，CSV 直接贴进工单系统。

**画面**：页签二 → 处置单卡片 → 生成工单预览 → 确认发送 → 切批量导出，展示 CSV 下载。

### 2:40–3:30 通用性：不吃"格式饭"

> 评委可能会问：换个企业的告警系统能用吗？演示导入模式——上传任意一份告警文件，**不需要改格式**。系统先猜列的角色，把"第一行样例值"摊开让你核对，点一下哪列是时间、哪列是内容即可。
>
> 文件里连"实体"列都没有？系统从告警文本里抽：IP、主机名、带编号的设备名（比如 Redis02）、服务名（svc-a），抽不出来就用模板差分兜底，并且把抽取结果摊给你核对。处理完同样得到分诊、窗口与根因排序。
>
> 路线 B 也不锁定任何厂商——侧边栏填入你自己的 API Key 和模型名，六大主流厂商加本地 Ollama 都能接，对任意窗口**现场调用**。密钥只存在浏览器会话内存，不写盘、不落日志。

**画面**：切"导入新告警流"→ 上传无实体列的示例 CSV → 列映射面板 → 抽取核对面板 → 现场调用按钮（可提前填好 key）。

### 3:30–4:10 诚实边界（主动讲）

> 最后主动说清楚这个系统的边界。第一，消融实验证明**新发告警是定位能力的开关**：有新发告警的故障窗口，规则路线 Top-1 达 87% 到 94%；没有的窗口我们定位不了——此时系统**明确拒绝下结论**，标注"证据不足、建议人工复核"，而不是编一个置信度。第二，网络类故障在纯 OS 层指标下 Top-1 为 0，需要调用链信号，这是已列出的改进项。第三，规则与融合的实验**先于结果定死**，三条实测不触发的规则也原样保留。
>
> 在告警洪水这个真实场景里，我们交出的不是"全能的 AI"，而是**一个可审计、知道自己在什么时候不能下结论的值班助手**。

**画面**：help.html 第 4 节"追问：常驻告警为什么反而不重要"的消融表格，镜头缓慢扫过数据。

### 4:10–4:30 收尾

> 从 10 万条告警到一张可派发的工单：**发生了什么、谁是根因、接下来怎么办**——三个问题，一个值班台。
>
> AlarmFlood Copilot，谢谢观看。

**画面**：回到标题页，淡出。

## 四、录制注意事项

1. **不要选 NETWORK 类窗口**做双路演示（Top-1 为 0 的已知边界），选 #41 或 #377；
2. 口播"47%、49%"时画面最好同时出现 experiments.md 的对比表或 help.html 的数据表，口播与画面互证；
3. API Key 那一步，**key 输入框是密码框**不会泄密，但录屏时别把已填 key 的明文留在别处；
4. 全程注意画面里不得出现学校名、队员姓名（公平性红线，已在代码与文档中清查过一遍，录屏前再检查浏览器标签页和任务栏）；
5. 若 3 分钟版本需求出现：砍掉第 7、8 步（导入模式），保留 0:00–2:40 与边界段，压到 3 分钟。
