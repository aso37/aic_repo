## 1. 方法

对每个可评测窗口：

```
fused(e) = α · rule_score(e) + (1 − α) · llm_conf(e)
```

| 分量 | 来源 | 值域 | 说明 |
|---|---|---|---|
| `rule_score` | `m3_rank.rank_entities(wdf, "rule")` | **[0,1]** | 四路 min-max 加权和、权重合计 1.0，**天然落在 [0,1]，无需再归一化** |
| `llm_conf` | `llm_rankings.json` 的候选置信度 | [0.1, 0.9] | **同一实体出现多次时取最大置信度** |

实体全集 = rule 的实体 ∪ LLM 的实体；LLM 未提及的实体记 0 分。本批数据中 **0 个窗口** LLM 无候选（若有则只用 rule，不计入 LLM 贡献）。

## 6. 附带发现：两处会让比较失真的口径问题

### 6.1 候选集口径不一致（影响 rule 与 llm 的可比性）

- `m3_rank.evaluate()` 对**窗内全部实体**排名 → `rule` 行是这个口径
- `m3_llm.py` 只对 **LLM 自己点名的实体**（≤5 个）排名 → `llm` 行是这个口径

当 LLM 点名少于 3 个实体时，两种口径会给出不同结论。实测反例：

| 窗口 | 类型 | 真值根因 | 窗内实体数 | LLM 点名数 | 原生 Top-3 | 全候选 Top-3 |
|---|---|---|---|---|---|---|
| #1872 | NETWORK | MG01 | 2 | 1 | `['Mysql02']` → 漏 | `['Mysql02','MG01']` → 命中 |

因此 LLM 的成绩是：**原生口径** 35/72 (49%) / 46/72 (64%)；**全候选集口径** 35/72 (49%) / 47/72 (65%)。

**建议**：对比表里三行统一用「窗内全部实体」口径（本文件第 3 节已如此），
或在表里加一列注明口径。

### 6.2 LLM 排名里的重复实体（会**低估** Top-3，非 bug）

实测 LLM 候选里**同一实体会重复出现**（同一实体被标了不同模板），例如：

```
rank1: apache01
rank2: apache01   ← 同一实体重复
rank3: MG01
```

重复项会**白占位置**：若直接用原始列表取前 3，去重后本可进前 3 的实体被挤掉，
因此原始口径会**低估** Top-3。

| 统计口径 | Top-1 | Top-3 |
|---|---|---|
| 原始列表（含重复，前 3 可能有重复项） | 35/72 (49%) | 45/72 (62%) |
| **按实体去重** | 35/72 (49%) | 46/72 (64%) |

有重复实体的窗口：**26/72**。
→ **`m3_llm.py` 的实现已按实体去重**（`candidates_to_entities()` 用 `e not in order` 过滤），得到 46/72 (64%)，与 `experiments.md` 里 llm 行的数字**一致** —— **这一项没有 bug**。本模块同样去重，以保持一致。

## 7. 结论

- 融合的**无偏**估计（5 折 CV）：Top-1 **33/72 (46%)**、Top-3 **45/72 (62%)**
- 单路线：rule 34/72 (47%) / 45/72 (62%)，LLM 35/72 (49%) / 47/72 (65%)
- ⚠️ 融合略低于最强单路线（-2 个窗口）。这是**诚实的负结果**：说明在当前数据上两条路线的分歧多为「一错一对」，简单加权无法自动择善。
- 互补性：融合救回 0 个单路都漏的窗口，同时弄坏 1 个单路能命中的窗口。

## 8. 局限（答辩如实说明）

1. **LLM 置信度未校准**：这里把 `confidence` 当作可直接与 rule 分数相加的量。
   实测其为 0.1~0.9 的 10 个离散值，是模型自报值，与真实正确率未必对应；
   若做置信度校准（如 isotonic / 分箱），融合还有提升空间。
2. **评测集偏小**：72 个窗口，交叉验证每折验证集约 14 个窗口，指标波动较大。
3. **LLM 结果只有一份**：单一模型（glm-4-plus）、单次运行，未做多次采样取平均。
4. **α 是全局单一值**：未按故障类型分别调 α（分类型调参会进一步放大过拟合风险）。
