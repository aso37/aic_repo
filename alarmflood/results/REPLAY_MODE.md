# 回放模式设计与验收（D5 · B 角色）

## 为什么需要回放模式

参赛要求 4 要的是「在线演示地址或可安装软件包」。在线演示最大的不确定性是
**运行时对 LLM API 的依赖**：评审点开的那一刻若遇到限流、欠费或断网，界面就会白屏或报错，
演示当场翻车。回放模式把这条依赖彻底移除——所有 LLM 相关计算都在**离线阶段**做完并落盘，
界面阶段只读产物。

## 两阶段划分

| 阶段 | 谁跑 | 做什么 | 产物 |
|---|---|---|---|
| 生成期（离线） | B 的 `m3_llm.py` / `m4_report.py` | LLM 根因排序、处置单与工单生成 | `results/llm_rankings.json`、`results/reports/window_*.json` |
| 回放期（演示） | C 的 `app.py` | 只读 parquet 与上述 JSON 渲染 | 无（纯展示） |

## 界面如何做到零 LLM 依赖

- 页签一「窗口详情」的根因卡：调用 A 的**纯 CPU 规则排序** `m3_rank.rank_entities`，不触网；
- 页签二「处置单」：直接读取预计算 JSON；
- 全程无 `openai` / `m3_llm` 引用——由 `scripts/check_replay.py` 做静态校验把关。

## 覆盖策略

- 处置单优先覆盖**告警量最大**的窗口；侧边栏按告警量倒序排列，保证默认打开即有内容。
- 尚未覆盖的窗口在页签二优雅降级为提示（页签一仍有规则根因卡可看），不会崩溃。

## 如何验收

```
python scripts/check_replay.py
```

四项检查（无 LLM 依赖 / 默认加载 / 派单按钮 / 无处置单降级）+ 覆盖统计，
结果写入 `results/replay_check.md`。

## 与"实时调用"的取舍

实时调用看起来更"智能"，但把演示成败交给外部 API 是不可接受的工程风险。
回放模式牺牲了"任意窗口即时生成"，换来演示的确定性——这正是要求 4 想看到的成熟度。
需要补充覆盖时，跑一次 `python modules/m4_report.py --min-alarms N` 重新生成即可，
不需要改界面。
