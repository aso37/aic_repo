## 2. 最大的发现：数据集没有"告警"，只有"原料"

**问题**：我们的方案入口是告警流（alarm flood），但翻遍数据集只有 metric/logs/trace——**没有现成的告警文件**。

**决策**：不换数据集，而是**自己当监控系统**——真实世界里告警就是监控系统对"指标越限"产生的（zabbix/Prometheus 告警规则就是这么工作的）。我们写 10 条阈值规则，从 metric 生成告警流：

```python
RULES = [
    ("OSLinux-CPU_CPU_CPUCpuUtil", 90.0, "CPU使用率{v}%超过阈值90%", 2),
    ("OSLinux-OSLinux_MEMORY_MEMORY_MEMUsedMemPerc", 90.0, "内存使用率{v}%超过阈值90%", 2),
    # ... 共 10 条，见 loaders/loader_aiops2021.py
]
```

**学习点**：数据不满足假设时，先问"真实系统里这个东西是怎么来的"——答案往往就是你的数据构造方案，而且这样构造的数据**有业务正当性**，答辩讲得通。

## 3. 难点一：时区陷阱（差 8 小时，差点污染所有结论）

**症状**：写探针脚本对比"故障窗口内的指标"时，先得到 58% 覆盖率；修正后变成 78%。中间差的那 20% 全是时区错位的假象。

**诊断过程**：
1. groundtruth 的 `st_time` 是字符串 `2021-03-04 11:50:00`（"数据时钟"）
2. 它自带的 `time` 列（毫秒）与字符串是**自洽**的：`pd.to_datetime(1614829800000, unit='ms')` 正好等于 `11:50:00`
3. 但 `Timestamp('2021-03-04 11:50:00').timestamp()` 在本机得到的结果比数据自带锚点**多 8 小时**——本机时区与数据时钟不一致

**解决**：所有 epoch 换算**以数据自带的 time 列为锚点**：

```python
st_ms = gt["time"].astype("int64")              # 锚点，绝对可信
ed_ms = st_ms + (ed_dt - st_dt).total_seconds() * 1000   # 时长差与 时区无关
```

并在代码里立下禁令：**禁止对这个数据集使用 `.timestamp()`**。

**学习点**：时间处理三原则——① 能用数据自带的时间戳列就绝不用字符串转换；② 时长差（ed - st）与时区无关，永远安全；③ 任何"看起来不对劲的比例"，第一怀疑对象是时间对齐。

## 4. 难点二：drain3 不做数字掩码就等于没用

**症状**：M1 跑完，"7 条消息 = 7 个模板"——每条都成了独立模板，归并完全失败。

**诊断**：终端有提示 `config file not found: drain3.ini`。drain3 的数字掩码（把 `92.3` 替换成占位符）是靠配置文件启用的，没配置时它把 `CPU使用率92.3%` 和 `CPU使用率93.7%` 当成两句话。

**解决**：编程式配置（不依赖 ini 文件，避免路径问题）：

```python
from drain3.masking import MaskingInstruction
from drain3.template_miner_config import TemplateMinerConfig

cfg = TemplateMinerConfig()
cfg.masking_instructions.append(MaskingInstruction(r"\d+(\.\d+)?", "NUM"))
miner = TemplateMiner(None, cfg)
```

配置后：`CPU使用率92.3%超过阈值90%` 和 `CPU使用率99.0%超过阈值90%` 正确归并为 `CPU使用率<NUM>%超过阈值<NUM>%`。

**学习点**：第三方库"能跑"和"结果正确"是两回事。drain3 没报错、没异常，只是安静地输出了错误结果——**验收标准（模板数、压缩比）必须提前定好**，否则这种静默错误会一路带到答辩。

## 5. 难点三：重复抑制与"告警状态"的语义

**背景**：原始 10 万条告警里 84% 是内存类——某些机器内存长期 >90%，每分钟都触发一次，这就是**重复报警/抖动报警**（工业报警治理里的 chattering）。

**做了什么**：实现抑制——同 (entity, alarm_id) 在 600 秒内只保留首条：

```python
def suppress_duplicates(alarms):
    keep = []
    for (_, _), g in alarms.groupby(["entity", "alarm_id"], sort=False):
        last = -10**18
        for i, ts in enumerate(g["timestamp"]):
            if ts - last >= SUPPRESS_WINDOW_S * 1000:
                keep.append(g.index[i]); last = ts
    return alarms.loc[sorted(keep)]
```

**新问题**：抑制后覆盖率从 78% 掉到 56%！

**原因**：故障窗口只有 5 分钟，如果某条告警的"上一次通知"恰好在窗口开始前几秒，那么窗口内它被抑制、窗口结束后才再通知——窗口里就"看不到"它了。

**解决**：想清楚语义——**抑制的是"重复通知"，不是"告警消失"**。告警状态在抑制窗口内持续生效。所以覆盖率检查时把窗口起点往前回看一个抑制窗口：

```python
m = a[(a["timestamp"] >= w["st_ms"] - 600_000) & (a["timestamp"] <= w["ed_ms"])]
```

修正后覆盖率 80%，还比抑制前高（因为补了 CPUUserTime 新规则）。

**学习点**：数据变换后指标变差，先别急着调参，**先检查指标的定义是否还匹配变换后的语义**。

## 6. 难点四：漏报分析（探针方法论）

**问题**：20% 的故障窗口里根因实体没有任何告警——为什么？

**方法**：写通用探针（`scripts/probe_missed2.py`）：对每个漏报窗口，取根因实体的全部 349 个指标，算"窗口内均值 vs 前 2 小时基线均值"的比值，找显著变化（比值 ≥2 或 ≤0.5）。

**发现**：

| 故障类型 | 漏报案例的信号 | 处置 |
|---|---|---|
| CPU（Redis02） | 总 CPU 只到 31%（阈值 90 漏掉），但用户态 CPU 从 0.2% 暴涨到 44.8%（229 倍） | ✅ 补规则 `CPUUserTime > 55`（正常 p99=47.5） |
| NETWORK（Tomcat02） | 单核 CPU-3 打满 100% | ❌ 放弃：实测正常负载下单核 100% 也很常见（p95=100），做规则会淹没信号 |
| MEMORY（apache01） | 所有指标纹丝不动 | ❌ 无指标级信号，需要看 logs（留到 D6） |

**学习点**：① 排查"为什么漏"要用**比值（相对变化）**而不是绝对值；② 补规则前先看该指标在**正常时段的分布**（p95/p99），否则按下葫芦浮起瓢；③ 有些信号做不了规则是正常结论，记录下来就是"已知边界"，答辩讲边界比假装全能更加分。

## 9. 知识卡片（讲给队友听）

- **告警状态 vs 告警通知**：告警触发后持续存在（firing），抑制只是不再重复通知——评测时要用"状态"语义
- **时区安全三件套**：自带时间戳列 > 时长差换算 > 显式 tz-localize；`.timestamp()` 对 naive 时间戳默认用本地时区，跨环境不可复现
- **Drain3 模板归并**：本质是"把句子里的可变部分（数字/IP）挖成占位符，再按句型聚类"；掩码规则必须显式配置
- **相对变化 > 绝对阈值**：故障注入类数据里，"从 0.7% 涨到 31%"比"绝对值超过 90%"更常见、更有检测价值
