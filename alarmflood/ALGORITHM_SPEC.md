# 核心算法说明（功能-算法映射）· B 角色主笔

> 对应用参考核要求 2：「AI 算法与产品功能深度契合，不脱节」。
> 本文用一张「功能-算法映射表」正面回答：界面上每一个功能，背后是哪个算法模块、解决什么问题。
> 数据口径：2021 银行场景，原始告警 101,478 条 → 抑制后 14,806 条；159 个故障窗口（112 train / 47 test）；检出 895 个洪水窗口。

## 一、功能-算法映射表（核心）

| 界面功能（用户在做什么） | 背后算法模块 | 解决什么问题 | 关键算法/指标 |
|---|---|---|---|
| 顶部时间轴（按小时告警量） | M1 模板归并 + M2 分诊 | 一眼看出"洪水"发生在哪个时段 | 抑制后 14,806 条的时间分布 |
| 侧边栏窗口列表（按告警量倒序） | M2 三级分诊 | 把十万级告警压成可逐个查看的窗口 | 895 个事件窗口；检测召回 79%（train） |
| 页签一 KPI 卡（告警数/实体数/模板数/时长） | M1 模板归并 + M2 分诊 | 量化窗口规模，判断"是不是洪水" | 模板压缩比 0.05%（7 模板 / 14,806 条） |
| 告警瀑布图（模板 × 时间） | M1 模板归并 | 展示各模板在窗口内何时首次出现、持续多久 | Drain3 + 数字掩码 |
| 三级分诊明细 + "新发告警实体"高亮 | M2 三级分诊 | 区分"背景噪声"与"真事件信号" | core/semi/novel 分层（99% 告警是噪声） |
| 根因候选 Top-5（score/新发数/首现时间） | M3 规则排序 `rank_entities` | 用确定性算法给出可审计的根因排序 | 0.5×新发数 + 0.15×新发越早 + 0.2×分层加权频次 + 0.15×共现 |
| 处置单页签（摘要/根因/处置建议/归并说明） | M4 处置单生成（LLM 撰写正文） | 把"根因"变成可执行的处置单 | LLM 结构化输出 + 幻觉校验 |
| "派单"按钮（工单卡片） | M4 工单字段（**代码确定性生成**） | 完成 human-in-loop 的最后一环 | 团队查 `teams.csv`、标题拼接、优先级定档 |
| 导出处置单 JSON | M4 落盘 | 交付物可下载、可追溯 | `results/reports/window_*.json` |
| 在线演示整体 | 全部预计算（回放模式） | 评审点开不依赖 API，演示确定性 | 运行时零 LLM 调用 |

**结论**：界面上不存在"凭空出现"的功能——每一块都锚定在一个算法模块上，且都能指出它解决了什么运维问题。这就是"不脱节"的直接证据。

## 二、各模块算法要点

### M1 告警模板归并

- 算法：Drain3 模板挖掘 + **显式数字掩码**（`\d+(\.\d+)?` → `<NUM>`）。
- 关键坑：drain3 默认不做掩码，`CPU使用率92.3%` 与 `93.7%` 会被当成两个模板（归并等于没做）。掩码必须用 `MaskingInstruction` 编程式配置。
- 产出：7 个模板 / 14,806 条告警，压缩比 0.05%。

### M2 洪水/事件窗口检测（本项目最重要的算法判断）

- 现象：教科书式「全局 mean+3σ 速率检测」在这份数据上失效——检出 210 个 1 分钟碎窗，全是噪声。
- 根因：99% 的告警是**常驻/周期性背景告警**（standing alarm，EEMUA 191 经典问题），周期重触发把速率检测淹没。
- 算法：**三级告警分诊**——按累计触发次数把"实体×规则"分为 core（≥900，背景噪声，不触发窗口）、semi（100~899，触发窗口）、novel（<100，真事件信号，强证据）。
- 设计思想：**检测灵敏度与排序精度解耦**——检测端宁多醒（semi 也触发窗口，保召回），排序端用分层权重去伪。

### M3 根因候选排序（规则 + LLM 双路线）

- 路线 A（规则，确定性、可审计）：`score = 0.5×新发告警数 + 0.15×新发越早 + 0.2×分层加权频次 + 0.15×分钟共现`。
- 路线 B（LLM，软推理）：把窗口内去重后的证据（首现时间/模板/次数/实体/**层级**）与「窗口概况」喂给 LLM，输出带置信度与推理链的根因候选。
- 关键发现：**prompt 决定成败**——仅给 tier 标签时 Top-1 只有 25%（不如规则）；显式给出"哪些实体有新发告警"+"常驻=噪声"的运维先验后升到 49%，反超规则（47%）。
- 消融证据：截断喂（只喂最早 5 条证据）降到 25%，证明判别性信号往往晚于背景告警出现，完整上下文不可省。

### M4 处置单与工单

- LLM 只负责写正文（摘要 / 根因 / 建议 / 归并说明）。
- **工单字段全部由代码确定性生成**：责任团队查映射表、标题拼接、优先级按"是否有新发告警+置信度"定档——保证"Agent 行动可审计"。
- 幻觉校验：根因实体必须出现在窗口证据中，违规打回重生成（≤2 次），仍失败降级为模板化处置单。

### M5 看板

- 纯展示层，读 M1-M4 的落盘产物；根因卡复用 M3 规则排序（纯 CPU）。
- **回放模式**：运行时零 LLM 调用，详见 `results/REPLAY_MODE.md`。
